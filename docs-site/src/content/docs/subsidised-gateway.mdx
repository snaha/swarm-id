---
title: Subsidised Gateway
description: Enable uploads for users without their own postage stamps
---

A subsidised gateway allows dApps to provide postage stamps on behalf of their users, enabling uploads even when users don't have their own stamps.

## Overview

Normally, uploading to Swarm requires a postage stamp — a cryptographic proof of payment for storage. Users must purchase stamps using BZZ tokens, which creates friction for new users.

With a subsidised gateway:

- The dApp operator runs a gateway that provides stamps for uploads
- Users can upload without owning stamps
- The dApp operator pays for storage on behalf of users

This is useful for:

- **Onboarding new users** who don't have BZZ tokens yet
- **Free-tier applications** where the operator covers storage costs
- **Users whose browser partitions storage** and whose session was handed no stamp of its own

## Configuration

Pass the `subsidisedGatewayUrl` option when creating the client:

```typescript
const client = new SwarmIdClient({
  iframeOrigin: 'https://swarm-id.snaha.net',
  subsidisedGatewayUrl: 'https://gateway.my-dapp.com',
  metadata: {
    name: 'My App',
    description: 'A decentralized application',
  },
})
```

The subsidised gateway URL should point to a Bee node that has a postage stamp configured for public use.

## Upload Availability Truth Table

Upload availability depends on three things. The `uploadMode` field in `client.connectionInfo` indicates which mode is active:

| Usable User Stamp | Custom Node | Subsidised Configured | Can Upload | Upload Mode   | Unavailable Reason |
| ----------------- | ----------- | --------------------- | ---------- | ------------- | ------------------ |
| Yes               | —           | —                     | Yes        | `user-stamp`  | —                  |
| No                | Yes         | (disabled)            | No         | `unavailable` | see below          |
| No                | No          | Yes                   | Yes        | `subsidised`  | —                  |
| No                | No          | No                    | No         | `unavailable` | see below          |

All four rows require an authenticated session. Without one `uploadMode` is `unavailable` with no reason given, even where a gateway is configured — uploads still need the app secret.

### Understanding the Table

**Usable User Stamp**

The session resolved a postage batch **and** its signer key **and** built a working stamper from them. All three, because the stamper is constructed asynchronously and a failure there is logged rather than thrown — a resolved batch is not on its own enough to upload with. User stamps always take priority over a subsidised gateway.

**Custom Node**

The user has configured a custom Bee node URL in the identity provider's network settings. When a custom node is set, the subsidised gateway is **silently disabled**, so that uploads go to the user's chosen node. That node must allow the identity UI's origin — see [Using Your Own Bee Node](/own-bee-node).

The check is an exact inequality against the default gateway URL, and it runs in two places: once when the dApp identifies itself to the proxy, and again whenever network settings arrive or change. The second matters for a storage-partitioned session, whose settings are handed over by the connect popup _after_ the dApp has identified itself. Reverting to the default URL does not re-enable a gateway already dropped — that takes a dApp reload.

**Subsidised Configured**

The dApp passed a `subsidisedGatewayUrl` when creating the SwarmIdClient.

**Storage partitioning is not one of the axes.** When the browser partitions storage (Safari ITP), the proxy iframe cannot **read** the user's postage stamps or Bee node setting out of the trusted domain's localStorage. Since [#277](https://github.com/snaha/swarm-id/issues/277) it does not have to: the connect popup hands both over directly. A partitioned session with a drive is therefore an ordinary `user-stamp` session — confirmed on real Safari, iOS 18.7 / Safari 26.6 ([#584](https://github.com/snaha/swarm-id/issues/584)). `ConnectionInfo.storagePartitioned` is still reported, for UI messaging; it does not decide whether you can upload.

A handover that arrives **without** the account view is refused outright, so there is no half-session to account for here: the session either has the account's own stamps to fall back from, or it was never established.

### Why Uploads Are Unavailable

When `uploadMode` is `unavailable`, `ConnectionInfo.uploadUnavailableReason` names the **first** thing that stopped the session, not the last symptom:

| Reason           | Meaning                                                                                                |
| ---------------- | ------------------------------------------------------------------------------------------------------ |
| `no-stamp`       | No postage batch or no signer key resolved — most often an account with no drive yet.                  |
| `stamper-failed` | The stamp resolved, but the write path did not build. The only place that difference reaches the dApp. |

The reason is `undefined` while the session is unauthenticated, and while `canUpload` is `true`.

## Checking Upload Mode

Read `client.connectionInfo` to check the current upload mode (synchronous, populated as soon as `initialize()` resolves):

```typescript
const info = client.connectionInfo
if (info.canUpload) {
  if (info.uploadMode === 'subsidised') {
    console.log('Uploads will use the subsidised gateway')
  } else {
    console.log('Uploads will use your postage stamp')
  }
} else {
  console.log(`No upload capability available: ${info.uploadUnavailableReason ?? 'not connected'}`)
}
```

## Priority Rules

1. **User's own stamp** — Whenever the session resolved one, partitioned or not, it is the stamp that is used
2. **Custom Bee node** — If the user has configured a custom Bee node, the subsidised gateway is disabled (even if configured)
3. **Subsidised gateway** — Used as a fallback when no user stamp is available

This ensures users retain control over their uploads while providing a fallback for those without stamps.

## Running a Subsidised Gateway

To provide a subsidised gateway for your dApp:

1. Run a Bee node with a funded wallet
2. Purchase a postage stamp with sufficient depth and amount for your expected usage
3. Deploy a gateway proxy (such as [swarm-gateway](https://github.com/ethersphere/swarm-gateway)) in front of your Bee node that automatically injects the postage stamp header for uploads
4. Expose the gateway via HTTPS
5. Allow the identity UI's origin in the gateway's CORS configuration — uploads are made by the Swarm ID iframe, not by the dApps you serve, so their origins are not the ones that appear. See [Using Your Own Bee Node](/own-bee-node#why-the-iframes-origin-is-the-one-that-matters)

The gateway proxy intercepts upload requests and adds the required postage stamp header, so clients can upload without providing their own stamp.

:::caution
Monitor your stamp's utilization and balance. When a stamp is depleted, uploads will fail. Consider automating stamp top-ups based on usage.
:::

## Security Considerations

- The subsidised gateway only provides stamps — it doesn't have access to user data or keys
- Uploads are still signed by the user's app key for feeds and SOCs
- Consider rate limiting on your gateway to prevent abuse
- The gateway URL is visible in the client configuration
