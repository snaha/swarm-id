Swarm ID is an authentication and identity management system for Swarm dApps. It gives a dApp a popup sign-in flow, in the style of OAuth, that works in Chrome, Firefox and Safari without a browser extension and without the Storage Access API. Where a browser partitions the proxy iframe's storage, Safari above all, the connect popup hands the iframe its credentials directly; see [Architecture](./architecture/) for what is confirmed on a real device.

## Key Features

- **Works in every major browser** - Chrome, Firefox and Safari, with no extension
- **One secret, many keys** - every key derives from the account's recovery phrase; see [Key Derivation](./key-derivation/)
- **Master key stays home** - the master key never leaves the trusted domain
- **One secret per app** - each dApp gets its own derived secret, so two apps never share one
- **Three ways to unlock** - a passkey, an Ethereum wallet, or a password
- **Backup and recovery** - an encrypted `.swarmid` file, plus restoration from Swarm on a new device
- **Drives** - postage batches bought in the app, shared by all of the account's devices
- **Live propagation** - a change reaches the account's open tabs, iframes and devices in about a round trip over the [account bus](./account-bus/)

## How It Works

Three parts:

1. **Trusted domain** - `swarm-id.snaha.net` hosts the identity UI, the keystore, and the two pages below
2. **Connect popup** - opened from a dApp, it unlocks the account and derives that dApp's secret
3. **Proxy iframe** - hidden in the dApp page, it holds the secret and makes every Bee request on the dApp's behalf

### Connecting a dApp

1. The dApp page embeds a hidden iframe from the trusted domain
2. The user clicks connect, and a popup opens on the trusted domain
3. The user creates an account or unlocks the existing one
4. The popup derives a secret for that dApp's origin from the master key
5. The secret reaches the iframe. When the dApp page and the trusted domain are same-site, the popup writes it to the shared store and the iframe picks it up from a storage event. When the browser partitions the iframe's storage, the popup posts it to the iframe through `window.opener` instead, together with the stamps the dApp may spend
6. From then on the iframe signs and sends every Bee request for that dApp

## Security Model

- **Master key isolation** - the master key lives only in the identity UI, encrypted at rest under the account's access method
- **Deterministic app secrets** - HMAC-SHA256 of the master key and the dApp's origin
- **Origin isolation** - the dApp page cannot read the iframe's storage; they are different origins
- **Validated messages** - every postMessage is checked against a Zod schema before anything acts on it
