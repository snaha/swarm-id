Multi-Device Postage Batches

This page is the definitive, implementation-level specification of how Swarm ID lets several devices that share one account write to a single mutable postage batch at the same time without corrupting each other’s data. It is written so the scheme can be re-implemented on another platform (native mobile, desktop, a different language) and interoperate with the reference TypeScript implementation in @snaha/swarm-id.

What is stored is derived purely from Swarm primitives (chunks, single-owner chunks, epoch feeds) and a handful of deterministic key derivations. Who may write a partition at a given moment is not stored at all: the contexts of an account that are open at the same time agree on it over the account bus, and a context that cannot reach the bus does not write a shared batch. A port has to speak that protocol too.

Two independent systems

Section titled “Two independent systems”

The account shares one batch across devices. Two distinct problems arise, solved by two independent mechanisms:

  1. Partition lanes — prevent two writers from stamping the same (bucket, slot) of the batch (which would make one chunk silently overwrite the other on the network). Each active context holds a partition of every bucket’s slot space and only ever stamps slots in its own lane.
  2. Account-state sync — keeps the account (connected apps, postage stamps, the device list, settings) converging across devices. Each device writes its own feed, and a reader folds every device’s latest view into one account.

They are independent: account-state sync would be needed even with one batch per device, and the lanes would be needed even if account state never changed. A context that holds a partition is also the one permitted to publish account state (the “partition gate”, below). The account bus cuts across both: it carries a snapshot to live peers ahead of the feed, and it is where a partition is asked for and handed over.

Key derivation (the interop root)

Section titled “Key derivation (the interop root)”

All cross-device addressing derives from the account’s derivation key (derivationKey), a 32-byte secret stored on the account and held by every device. Two devices interoperate if and only if they derive the same keys from the same derivation key. Where the derivation key itself comes from is on Key Derivation.

Its Ethereum address (backupSigner.publicKey().address()) is the owner of every feed and every single-owner chunk in this document. Because the owner is per-account, the same identifier/topic across two different accounts still produces different chunk addresses — domain separation comes from the owner, not from baking the account ID into hashes.
  • swarmEncryptionKey encrypts the state-pointer entries and the account feeds, and seeds the per-utilization-chunk key derivation.

Per-device identity:

  • deviceId — a per-install UUID (crypto.randomUUID()), stored under the localStorage key swarm-id-device-id. Stable for the life of the install; not derived from the account, so each device has a distinct one.

Batch slot layout & partitions

Section titled “Batch slot layout & partitions”

A Swarm postage batch of depth D has:

  • NUM_BUCKETS = 65 536 buckets (2^16, BUCKET_DEPTH = 16).
  • 2^(D-16) slots per bucket (calculateMaxSlotsPerBucket).

The slot space of every bucket is divided into PARTITION_COUNT = 2 interleaved lanes. The lowest PARTITION_COUNT slots are reserved (not data):

  • Slot index p (for p in [0, PARTITION_COUNT)) is reserved for partition p’s counter (utilization) chunks and state-pointer entries.
  • Data slots begin at DATA_COUNTER_START = PARTITION_COUNT.

So with K = 2: partition 0 writes data to slots {2, 4, 6, …}, partition 1 to {3, 5, 7, …}, and slots {0, 1} are the two partitions’ reserved slots. The lanes never collide, so two devices on different partitions can stamp the same bucket concurrently.

Legacy single-device accounts use partitionCount = 1 (reserved slot 0, data from slot 1 onward) and have no lanes.

Utilization tracking

Section titled “Utilization tracking”

Each device tracks, per bucket, how many data chunks its partition has written — the j counter above. This is held in memory as a Uint32Array(65536) (dataCounters), always uint32 in memory regardless of how it is serialized.

The local cache’s codec

Section titled “The local cache’s codec”

This is the layout of the device’s own cache and utilization backup, not of the published partition state (see Wire format for that). The counter array is serialized into fixed CHUNK_SIZE = 4096-byte chunks. The per-bucket counter is uint16 when it always fits (D ≤ 31, max 2^15), else uint32 (D ≥ 32). This sets the chunk layout (getChunkLayout):

Codec Applies when bucketsPerChunk numUtilizationChunks
uint16 D ≤ 31 2 048 32
uint32 D ≥ 32 1 024 64

Counters are little-endian in the serialized chunk. Chunk i covers buckets [i·bucketsPerChunk, (i+1)·bucketsPerChunk).

Per-chunk encryption key

Section titled “Per-chunk encryption key”

Utilization chunks are uploaded as encrypted content-addressed chunks. The key for chunk i is deterministic so re-saves dedup:

nonce starts at 0 and is incremented only when the resulting encrypted address would land in the same bucket as another utilization chunk in the same save (collisions are vanishingly rare — ≈0.008 bumps per save with 32 chunks over 65 536 buckets). The nonce that produced a chunk is cached so an unchanged plaintext reuses the same key and the upload is skipped.

Local cache

Section titled “Local cache”

The reference implementation caches counter chunks in an IndexedDB store (UtilizationStoreDB, DB name swarm-utilization-store), keyed by (batchId hex, chunkIndex), storing { data, contentHash, nonce, lastAccess }. A port may use any local KV store; the cache is an optimization, not part of the wire protocol. What a device resumes from across devices is the published partition state (below), not the cache.

Who holds a lane

Section titled “Who holds a lane”

A lane is one partition of one batch. Nothing on Swarm says who holds it. The contexts of the account that are open right now (a tab, an embedded iframe) agree on it by exchanging a few small messages over the account bus. The protocol is small, and it was model-checked before it was built (models/bus-lease).

What a participant is

Section titled “What a participant is”

One context, for as long as its connection to the signaling server lasts. Its name is the peer id the server gave that connection. Two tabs of one browser are two participants. A context that reconnects is a new participant and holds nothing.

What the bus must provide

Section titled “What the bus must provide”
  • A confirmed connection. The server asks every room member to ping every 2 s (tick), and answers each ping with a pong. A context’s connection is confirmed as of the moment it sent the newest ping that was answered.
  • The room. The server tells every member who joins and who leaves. A member that stops answering ticks is dropped.

The rules

Section titled “The rules”
Constant Value Meaning
LEASE_STOP_MS 6 000 ms A holder whose connection has not been confirmed for this long stops.
LEASE_WAIT_MS 8 000 ms How long everyone else must have been absent before a lane is taken.
  1. Writing. A context stamps only while it holds the lane and its connection was confirmed less than LEASE_STOP_MS ago. A confirmation that arrives after a longer gap means the context holds nothing any more.
  2. Claiming. A context that wants a lane sends lane-claim with a fresh random round, to everyone, and again with every confirmation while the claim is open.
  3. Taking. The claimant holds the lane once every other context has either answered lane-free for that round, or has been absent from the room for LEASE_WAIT_MS. A context whose own stay in the room is shorter than that cannot know who left before it came, and waits. A message from a context the room does not list restarts that context’s absence.
  4. Answering a claim.
    • Not holding and not claiming the lane: answer lane-free.
    • Claiming it too: the lower peer id keeps its claim; the higher one drops its own and answers lane-free.
    • Holding it: stop stamping, then answer lane-free (a handover), or keep the lane and answer lane-held. The reference holder keeps it while an upload is in flight, for 3 s after one, and when the claim is marked gentle. lane-held is a courtesy: no rule reads it, and the lane is just as safe if it is lost.
  5. Every context answers, also for lanes of batches it never writes. A claimant waits for everyone present.

Messages may be lost, late, repeated or reordered; the rules hold regardless. A message whose from is not the peer that delivered it is dropped.

Which lane

Section titled “Which lane”

The reference client asks for every lane with gentle: true first, so it takes a lane nobody holds and leaves holders alone. Only once every lane has answered lane-held does it ask the holder of its home lane to hand over, and after each further 1.5 s the holder of the next lane. The home lane is

A blocking write keeps asking for 30 s before it fails. Nothing is released on a timer: a holder keeps its lane while its tab is open and connected.

Partition state

Section titled “Partition state”

Each (batchId, partition) has its own published counter: the holder’s per-bucket data counter. The holder publishes it on every upload; the next holder reads it when it takes the lane and resumes from exactly that counter, so a hand-off never re-uses a slot.

A write is reported complete only after the partition state that covers its slots is published. An upload that was still in flight when a holder disappeared was therefore never acknowledged, and the next holder may safely overwrite its slots.

The counter is not a single blob. It is packed into leaves under a frame (see Wire format below), each leaf uploaded with a random encryption key to the partition’s reserved slot, yielding a 64-byte encrypted reference (address ‖ key). A single reference chunk carries the frame, the exceptions and those references (7 + 8·E + 64·L bytes, one chunk at the width cap). A taking-over device follows pointer → reference chunk → leaves, decrypting each from its embedded key.

The state pointer

Section titled “The state pointer”

Each publish writes the reference chunk’s address as the next state-pointer entry: entry 1, 2, 3, …, each a SOC written once and never rewritten.

A reader searches for the highest entry: it reads the powers of 8 to bracket the answer, then splits the bracket 8 ways until it is one entry wide. Each round is a handful of reads made at once. A device that remembers an entry starts from it, and when nothing newer was published the lookup is a single round. The lookup uses no clock, so it finds a state however long ago it was written.

Entries share the partition’s reserved slot, so a later write in the same bucket replaces an earlier entry. The search is fixed (which entries it reads depends only on the answer), which leaves at most 60 entries that a later search depends on. A writer keeps its counter and reference chunks out of their buckets, and salt picks, by a rule the reader repeats, the first of 8 candidate addresses whose bucket is clear of the earlier entries on the entry’s search path.

A search in which the read of a possibly newer entry timed out is inconclusive: fail safe, read-only, retry later, never seed a zero counter. A holder never writes an entry twice: when it does not know the newest entry for sure, it searches before it publishes.

Wire format (byte layout)

Section titled “Wire format (byte layout)”

The format is binary and is versioned by the topic domain; there is no in-blob version byte. A new version publishes under its own topic and never collides with older readers: v1 was a fixed-width uint16/uint32 layout, left unread where it is.

The counter table is packed with the leaf encoding of Nectar’s SBU1 usage snapshot (docs/spec/sbu1.md §4 and §6; lib/src/sync/counter-codec.ts), byte for byte, so its golden vectors pin ours. A frame is a base (at most the smallest counter) and a bit width w (0 to 23). Every bucket stores count − base as a w-bit field, packed MSB-first with no gaps; a bucket whose delta does not fit is an exception: its field is all ones and its absolute count is listed in the reference chunk (at most 128). A leaf holds floor(32768 / w) buckets, so L = ceil(65536 / floor(32768 / w)) leaves cover the table (none at w = 0), the last one short. The canonical encoder takes base = min and the width that minimizes the packed bits plus 8 bytes per exception plus a digest per leaf — under the 128-exception cap, the narrowest width that fits.

The width follows the spread of the counters, not the batch depth, so a dilute changes no published byte. Lane counters are Poisson over the buckets, so the spread grows with the square root of the fill and a real drive packs into far fewer chunks than the fixed width before it took (32 at uint16, 64 at uint32):

Data written by one lane w Leaves
300 MB 3 7
2.5 GB 5 11
25 GB 7 15
1 TB 9 19
16 TB 11 23

Reference chunk — 7 + 8·E + 64·L bytes, big-endian, within one chunk at the width cap:

Offset Size Content
0 1 Width w
1 4 Base
5 2 Exception count E
7 + k · 8 4 Bucket of exception k (strictly ascending)
7 + k · 8 + 4 4 Its absolute count
7 + 8E + i · 64 32 Swarm address of leaf i, or all zeros if never written
7 + 8E + i · 64 + 32 32 Decryption key of leaf i (random, generated per publish)

A leaf whose bytes are all zero is not uploaded; its entry in the reference chunk is all zeros and the reader treats it as a zero leaf.

Leaf i — ceil(n · w / 8) bytes for the n buckets it covers: their deltas packed MSB-first, the trailing padding bits zero.

The decoded result is always a Uint32Array(65536). writePartitionState validates its input against PartitionStateSchemaV1; readPartitionState validates the reference chunk against the frame it names, each leaf’s length and padding, the exception list, and the reassembled counter before returning. There is no checksum: each reference binds its leaf’s exact bytes.

Incremental publish

Section titled “Incremental publish”

The previous publish’s frame is kept while it still fits the counter, so leaf boundaries hold and only the leaves a write touched are re-uploaded. A frame that no longer fits packs under the canonical frame and publishes every non-zero leaf. A context that takes a lane seeds this baseline from the state it read, so even its first publish is incremental. The baseline must be exactly the counter the kept leaves encode: a kept leaf goes out under an exception list computed from the new counter, and one that encodes any other counter is a leaf the reference chunk does not describe.

Read semantics

Section titled “Read semantics”

A context that finds nothing newer than a state it read or wrote itself downloads nothing and keeps its own counter.

When the pointer exists but the reference chunk or any leaf cannot be read, or fails the checks above, the read reports failure without caching the bad reference, and the device falls back to read-only without claiming the partition, retried on the next acquire. It must not seed a zero counter: stamping from zero would re-issue every used slot and evict the partition’s data chunk by chunk.

Both sides also protect the published chunks from later overstamps: the publisher avoids the buckets of its live utilization chunks, and every device records the published state chunks’ buckets so its own utilization saves avoid placing chunks there. All of these chunks share the partition’s reserved slot, and a collision would evict the resume point a later takeover depends on.

Historical: lock chunk and device-claim feed

Earlier iterations recorded the holder on Swarm: first a per-device claim feed, then a per-partition lock SOC rewritten in place, with beacon chunks beside it. Rewriting one address proved unreliable on real nodes, and none of it is in the library any more. A fresh port does not need it.

Taking over a partition

Section titled “Taking over a partition”

A context that has taken a lane reads the partition state before it stamps:

  • Nothing published (a clean search finds no pointer entry): start from a zero counter.
  • A published state: resume from exactly that counter. An unclean stop that stamped past its last publish loses only uploads that were never reported complete.
  • A state that may exist but cannot be read: do not write. Give the lane back and try again later.

A context that takes a lane it held before, with nothing published since, may keep the counter it has in memory. It must not trust a counter cached by another context of the same browser.

After each upload the holder publishes the counter and only then reports the upload complete. Before publishing it checks that it still holds the lane.

Account-state sync

Section titled “Account-state sync”

Account state is one feed per device, folded on read. There is no shared document, so two devices never write the same address and there is nothing to arbitrate. The design record is docs/Account-State.md.

Every feed is owned by the backup signer and its payload is encrypted with swarmEncryptionKey. Feeds are told apart by topic, not by signer, which is safe because every device is the same user and already holds derivationKey.

Roster feed

Section titled “Roster feed”

swarm-id-roster-v1:<accountId>, a sequential feed. Each device appends only its own Device record, at the next free index, so a concurrent announce can never overwrite a peer’s entry. The worst case is two devices racing for the same fresh index; the loser’s record is appended again on its next sync. Readers scan the feed in parallel windows and fold the entries by deviceId. A device appends only when it is missing from the roster or its removedAt state changed, so the roster is written rarely.

Device-state feed

Section titled “Device-state feed”

swarm-id-devstate-v1:<accountId>:<deviceId>, an epoch feed whose latest entry is the device’s full current view (DeviceStateSnapshotSchemaV1):

A device writes its feed on a local change, never after a read, so write amplification is bounded and folding is repeatable. Both writers go through the batch write coordinator (the cross-tab lock plus a held partition): the identity site publishes once per change, and the proxy iframe publishes with a short debounce when it takes a partition or sees a local change.

Read: the fold

Section titled “Read: the fold”

foldAccountFromSwarm derives the owner and the encryption key, reads the roster (an empty roster means there is no backup), reads every non-removed device’s latest view in parallel, and folds them:

Collection Recency clock Tombstone
postage stamps deletedAt ?? createdAt deletedAt
devices max(removedAt ?? 0, lastSignedInAt) removedAt
connected apps max(revokedAt ?? 0, disconnectedAt ?? 0, lastConnectedAt) revokedAt

Last writer wins by that clock; tombstones are kept, and a later activity with a larger clock brings an entry back (a removed device signing in again, for example). Fields that are plain edits rather than statements of membership — a device’s name, a stamp’s name, an app’s drive pointer — each ride their own clock and are laid over the winner, so a rename made on a stale copy cannot outrank a revoke made elsewhere. The four scalars converge per field on their at clocks, so concurrent changes to different scalars on different devices both survive. A winning deleted: true makes every other device forget the account; a restore writes deleted: false on a fresh clock and brings it back. A device that stays offline until the default drive expires never reads the deletion, and keeps the account.

Restore, refresh, and the bus

Section titled “Restore, refresh, and the bus”
  • Restore (a device signing in to an account it has never seen): fold from Swarm and create the account from the result.
  • Refresh (a device that already has the account): fold from Swarm and merge the result into the local account with the same rules, without publishing anything back.
  • A peer’s bus message: an account-delta on the account bus is folded with the same rules, so live peers converge in about a round trip. A change folded from a peer is never published back at it.

The partition gate

Section titled “The partition gate”

A context may publish account state only if it holds a partition (or can take one), because publishing writes chunks to the shared batch. If every partition is held by a context that is writing, or this context cannot reach the account bus, the publish is skipped and a peer publishes instead.

Porting checklist

Section titled “Porting checklist”

To interoperate with the reference implementation, an external client must:

  1. Reconstruct the same derivationKey after auth, then derive swarmEncryptionKey and backupKey via deriveSecret exactly as above (HMAC-SHA256, key-as-hex-bytes, context-as-UTF-8). The backupSigner address is the owner of everything.
  2. Generate a stable per-install deviceId (UUID).
  3. Implement the lane protocol on the account bus: the confirmed connection, the messages, and all five rules. A port that writes without holding a lane, or that does not answer claims, breaks every other client of the account.
  4. Implement the slot formula slot = K + p + K·j and route the counter chunks and the state pointer to reserved slot p. Honour PARTITION_COUNT = 2, DATA_COUNTER_START = 2.
  5. Implement the partition state: the topic hash, the numbered state-pointer entries and their search, the reference chunk with its frame and exceptions, the SBU1 leaves, publish-before-acknowledge, and the fail-safe (read-only, never zero-seed) handling of an unreadable published counter. Skipping the last one re-introduces silent slot-reuse data loss.
  6. Track per-bucket counters. The uint16/uint32 codec and the swarm-id-util-chunk-v1 key derivation describe the reference client’s own cache and backup; a port needs them only to read those.
  7. Implement account-state sync: the append-only roster feed, one device-state epoch feed per device with the snapshot schema above, and the fold with its recency clocks and tombstones.
  8. Respect the partition gate: never publish account state without holding a partition.

All hashes are keccak256; multi-byte integers in identifiers and topics are big-endian (uint32 for partitions, uint64 for epochs); serialized counters are little-endian; every feed and SOC is owned by the backup signer.
