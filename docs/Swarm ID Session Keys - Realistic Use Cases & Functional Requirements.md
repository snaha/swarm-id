# **Swarm ID Session Keys**

## Realistic Use Cases & Functional Requirements

This document outlines practical use cases for **Snaha Session Keys**, focusing on the delegation of temporary authority from a **Persona (Identity)** to a client application. These examples are designed to guide the Snaha team in implementing node-independent identity solutions for Swarm, satisfying the constraints of time-bound validity, ACT (Access Control Trie) integration, and permission permanence.

## **Core Concept: The Snaha Session Key**

A **Session Key** is a temporary cryptographic key pair generated by a client application (e.g., a web browser or mobile app). It is linked to a user's **Persona** via an **Authorization Mechanism** (specific implementation to be defined by the team).

- **Temporary Proxy:** The Session Key acts on behalf of the Persona for a limited time.
- **Time-Bound:** Valid only for a specific window (e.g., Start_Time to End_Time).
- **Revocable:** Automatically invalid after expiry; explicitly revocable before expiry.

## **Use Case 1: Gated Live Streaming (Consumption)**

_A user watches a pay-per-view event using a browser-based dApp._

### **Actors**

- **Viewer Persona:** The identity that subscribed to the content (purchased access).
- **Streaming dApp:** A web application running in the user's browser.
- **Swarm Gateway:** The node serving the encrypted stream chunks.

### **Pre-conditions**

1. **Viewer Persona** has purchased access, granting them permanent (or subscription-based) access to the stream's ACT.
2. The **Streaming dApp** does not have access to the Viewer's Master Key (for security reasons).

### **The Session Key Workflow**

1. **Initialization:** The user logs into the Streaming dApp. The dApp generates a temporary **Session Key Pair** (SK_Pub, SK_Priv).
2. **Delegation:** The dApp requests authorization. The user approves via their Swarm Wallet (Persona).
   - _Action:_ The Wallet generates a proof linking SK_Pub to Viewer Persona for **2 hours**.
3. **Accessing Content:**
   - The dApp requests encrypted chunks from Swarm.
   - The dApp presents the **Session Key** and the **Authorization Proof** to the decryption logic (client-side, Bee node or remote gateway).
   - Because the Viewer Persona is on the ACT, and the Authorization is valid, the dApp can unwrap the decryption keys using SK_Priv (via the ACT's derived session logic).
4. **Expiry:** After 2 hours, the session key expires.

### **Post-Expiry State**

- **Content Access:** The Streaming dApp stops working. Even if an attacker extracts the SK_Priv from the browser memory, they cannot use it to decrypt the stream or watch the VOD replay, because the authorization proof is no longer valid.
- **Persona Safety:** The Viewer's subscription remains intact on the ACT. They can generate a new session key to watch again.

## **Use Case 2: Third-Party File Manager (Management)**

_A user grants a gallery app temporary permission to back up photos to their personal Swarm Drive (Feed/Manifest-based construct)._

### **Actors**

- **User Persona:** The owner of the Swarm Drive.
- **Gallery App:** A third-party mobile application.

### **Pre-conditions**

1. **User Persona** owns a private Feed/Manifest (Swarm Drive).
2. The user wants to back up photos but does not want to give the Gallery App permanent access to their master wallet.

### **The Session Key Workflow**

1. **Request:** The Gallery App requests permission to upload photos.
2. **Delegation:** The User Persona authorizes a session key valid for **1 Hour**.
3. **Upload Action:**
   - The Gallery App prepares a file and stamps it.
   - The Gallery App uses the **Session Key** to sign the **Feed Update** (updating the directory manifest).
   - Swarm nodes (or the verification layer) accept the Feed Update by validating:
     1. The signature matches the Session Key.
     2. The Session Key has a valid authorization link from the Feed Owner (User Persona).
     3. The timestamp is within the validity window.
4. **Expiry:** The session ends.

### **Post-Expiry State**

- **App Control:** The Gallery App loses the ability to write (upload) to the user's drive. It cannot change file metadata after the granted window.
- **Content Persistence:** All photos uploaded during the session remain safely stored and owned by the User Persona.

## **Use Case 3: Creator Granting Access (Distribution)**

_A creator uses a mobile studio app to sell a digital asset to a fan, granting them permanent access._

### **Actors**

- **Creator Persona:** Owner of the content.
- **Fan Persona:** The buyer.
- **Studio Mobile App:** The tool used by the Creator.

### **Pre-conditions**

1. **Creator Persona** has a high-value video file encrypted on Swarm (ACT-gated).
2. **Fan Persona** has paid for the video.
3. The Creator is using a borrowed device or a lightweight mobile app and uses a temporary Session Key for security.

### **The Session Key Workflow**

1. **Delegation:** The Creator authorizes the Studio App with a **Session Key** valid for **15 minutes**.
2. **Granting Access:**
   - The Studio App calculates the new ACT (Access Control Trie) structure, adding the **Fan Persona's Public Key**.
   - The Studio App uses the **Session Key** to sign the update to the Access Control Grantee list.
   - The update is propagated to the Swarm network.
3. **Expiry:** The Creator logs out, or the 15-minute window closes.

### **Post-Expiry State**

- **Fan's Access:** The Fan **retains access indefinitely**. The action taken (updating the ACT) was valid _at the time it was performed_. The expiration of the Session Key does **not** revert the changes made to the ACT.
- **Creator Security:** If the Studio Mobile App is compromised later, the attacker cannot grant access to new users because the Session Key is expired.

## **Use Case 4: Real-Time Collaborative Editing**

_A team collaborates on a shared document using a decentralized editor._

### **Actors**

- **Editor Personas (Alice, Bob):** Team members.
- **Collab App:** A web-based text editor.

### **Pre-conditions**

1. A shared document exists as a mutable resource (Feed) on Swarm.
2. Alice and Bob have permission to edit.

### **The Session Key Workflow**

1. **Session Start:** Alice logs in for a work session. Her Wallet authorizes a **Session Key (8 hours)** for the Collab App.
2. **Editing:**
   - Every keystroke/save generates a small update or message (Feed/Swarm-based notification).
   - The Collab App signs these updates with Alice's **Session Key**.
   - Bob's client verifies the updates by checking Alice's Session Key validity against her Persona (using her Persona Public Key to verify the authorization).
3. **Revocation (Edge Case):** Alice loses her laptop. She uses her Master Wallet to broadcast a revocation for that specific Session Key.
4. **Instant Lockout:** Bob's client sees the revocation and immediately stops accepting updates signed by the compromised Session Key, even though the 8 hours haven't passed.

### **Post-Expiry State**

- **Document Integrity:** All edits made by Alice _before_ expiry/revocation remain part of the document history.
- **Future Edits:** Alice must re-authenticate and generate a new Session Key to continue editing.

## **Summary of Requirements for Snaha**

| Feature                  | Requirement                                                                                                                                                       |
| :----------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Delegation Mechanism** | An agnostic method to cryptographically link a Session Key to a Persona (e.g., via signature, smart contract, or specific message type) defined by the R\&D team. |
| **Validation Logic**     | Swarm Clients must be able to verify the chain of trust from Session Key \-\> Persona.                                                                            |
| **ACT Compatibility**    | The ACT protocol must accept a valid Session Key as a proxy for the Owner/Grantee during encryption/decryption operations.                                        |
| **State Permanence**     | Actions that modify the global state (uploads, ACT updates) must persist independently of the Session Key's lifecycle.                                            |

###

### **Optional / Future Research Areas**

- **Granular Scope:** Restricting Session Keys to specific actions (e.g., "Read-Only," "Upload-Only," "Sign-Only"). While valuable, this adds significant complexity to the verification layer and is treated as a "Nice-to-Have" for future iterations.
