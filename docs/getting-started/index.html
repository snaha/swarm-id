Quick Start

Install the package, create a client, call connect(). That is the whole integration; the rest of this page is what happens around it.

Install

Section titled “Install”
  • pnpm
  • npm
  • yarn

Connect and upload

Section titled “Connect and upload”

Every new account starts without a drive

A drive is what pays for uploads, and a fresh Swarm ID has none. Without a subsidised gateway, the first upload of every first-time user fails: canUpload is false and uploadUnavailableReason is 'no-stamp'. Downloads and key derivation work regardless.

Two ways to handle it, and most apps do both:

  • Pass subsidisedGatewayUrl. Uploads from accounts with no drive go through that gateway, which stamps them (uploadMode becomes 'subsidised'). The public gateway at https://api.gateway.ethswarm.org/ is fine for development and demos; see Using the public gateway for its limits.
  • Send the user to add a drive. When uploadUnavailableReason === 'no-stamp', link to the identity site’s Storage tab (https://swarm-id.snaha.net/#storage). Once the user has a drive, the session uses it in preference to any gateway.

Browser only

Importing the package is harmless anywhere, but constructing a client touches window. In a framework that renders on a server (Next.js App Router, SvelteKit with SSR, Nuxt), construct it in code that only runs in the browser: an effect, onMount, or a branch on typeof window !== 'undefined'. There is no server-side client yet (#770). A server or an agent that writes to Swarm goes through @ethersphere/bee-js directly with the drive’s batch id and signer key, stamping each chunk so the user’s own drive is spent through the public gateway. See The Public Gateway.

Data

Section titled “Data”

Everything below needs a connected user. Call client.connect() or let the iframe button do it.

Upload and download bytes

Section titled “Upload and download bytes”

What uploadData stores is raw bytes with no manifest. Read it back with downloadData, or from a gateway at /bytes/<reference>; downloadFile and /bzz/<reference>/ cannot resolve it.

An encrypted reference is a capability, not an address. The 128-hex reference from { encrypt: true } contains the decryption key, so whoever holds it can read the content. Treat it as a secret: never put it in a public index, an on-chain record or a gateway URL. If something public has to point at the content, publish a hash of the reference and hand the reference itself to the reader over a channel you trust. Every encrypted chunk is padded to 4 KB and its span is encrypted, so the exact byte length is hidden, but the number of chunks is not; if the size of a payload alone says something, pad or bucket it before upload.

Upload and download files

Section titled “Upload and download files”

uploadFile wraps the bytes in a manifest that carries the filename, so its reference is read back with downloadFile. The two pairs do not cross. uploadFile encrypts by default, and its 128-hex reference carries the key: a gateway’s /bzz/<reference>/ is only for a plain reference, uploaded with encrypt: false.

A batch you were given

Section titled “A batch you were given”

A postage batch (a drive in the identity site) is not an identity. If someone hands you a batch id and the private key that owns it, as hackathon gift codes do, create or sign in to a Swarm ID however you like, then attach the batch: Storage → Add drive → Use existing batch, with the batch id and the signer key. From then on every app the account connects can upload with it. On a new device, restore the account from its recovery phrase and the batch comes back with it.

Run it locally

Section titled “Run it locally”

Open http://localhost:3500. The demo runs on port 3500, the identity site on 5500, and the account bus signaling server on 5520. No HTTPS, certificates or custom domains: localhost is a secure context.

For a local Bee cluster, tunnels for real-domain testing, and the known dev keys, see Local Development.

Backup and recovery

Section titled “Backup and recovery”

These happen on the identity site, not in your app. The user exports an encrypted .swarmid file there, restores it with the recovery phrase, or rebuilds the account from Swarm on a new device. Architecture has the file format and the flows.
